# red-before-fix — доказать, что тест ловит баг, откатом источников

## Когда

- Написан тест на баг и фикс в одной порции, и нужно знать, что тест
  вообще падает без фикса (а не зелёный от рождения).
- Фикс и тест делались в одном рабочем дереве, без отдельного коммита
  «только тест» — стандартная ситуация при цепочке багфиксов.
- Ревью спрашивает «а тест точно проверяет это?» — ответ одной командой.

## Как

1. Снять дифф исходников (не тестов) в патч:
   `git diff -- <Sources dir> > $S/fix.patch`.
2. Откатить исходники к базе, тесты оставить:
   `git checkout -- <Sources dir>`.
3. Прогнать тест-таргет и сохранить вывод: ожидается красный именно на
   новом тесте, остальные зелёные.
4. Вернуть фикс: `git apply $S/fix.patch`; прогнать снова — зелёный.
5. В коммит-сообщение — одна строка: «без фикса тест X падает на …».

## Нюансы и грабли

- Тест, который использует новый API фикса (новое свойство, новый
  параметр), без фикса не компилируется, и красный не получить. Либо
  временно убрать эту строку теста на шаг 3 и вернуть на шаге 4, либо
  разбить: сначала API без поведения, потом поведение.
- Старый баг может не падать, а крашить тест-процесс (unowned-чтение,
  precondition): тогда «красный» — это падение всего прогона. Это тоже
  доказательство, зафиксировать в сообщении коммита.
- Патч делать по директории исходников, а не `git stash`: stash утащит и
  тест, и придётся выковыривать его обратно.
- Проверять `git status` после `git apply`: откат директории плюс
  патч должен давать ровно исходный дифф, ни одного лишнего файла.
- Шаг 3 гонять на том же тест-раннере, что и обычный прогон (для SwiftPM —
  `swift test --package-path <package>`), иначе красный может быть от
  другой причины.

## Вариации

- **Серия багфиксов**: один патч на фикс, тест-таргет гоняется N раз; в
  логе коммитов каждая запись «red → green» сама по себе.
- **Мутационная проверка**: вместо полного отката убрать одну строку
  фикса — показывает, какая именно строка держит тест.
