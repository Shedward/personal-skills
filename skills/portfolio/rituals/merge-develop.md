# Подлить develop в портфель и активные ветки

Сначала влей `origin/develop` в портфель и опубликуй проверенный результат. Затем влей **один и тот же опубликованный коммит портфеля** в каждую выбранную ветку MOB. Каждая MOB стартует со своей серверной вершины.

## Выбрать ветки и завести задачу

Определи портфель по [снимку](../SKILL.md#снимок-портфеля). Сразу заведи одну карточку `make` через [todo](../../todo/SKILL.md) **в группе портфеля**, даже если запрос пришёл из чата MOB. Если этот подлив уже начали, продолжи его карточку. Укажи исполнителя и текущий шаг по правилам `todo`.

Обнови снимок через `collect.py --refresh` с ключом портфеля. Для каждого дочернего тикета сверь статус в трекере, серверную ветку и фактические head, base и состояние PR. Рабочее определение активной ветки — тикет ещё открыт, ветка существует на сервере и её изменения ещё не влиты в портфель.

| Что удалось подтвердить | Действие |
|---|---|
| Тикет открыт, у него одна рабочая ветка и открытый PR в портфель | Включи ветку. |
| Тикет завершён и его изменения уже в портфеле | Пропусти, даже если ветка ещё есть на сервере. |
| PR отсутствует, закрыт без слияния или нацелен в другую MOB. Найдено несколько веток, статусы расходятся либо сведения устарели | Назови ветку и причину сомнения. Спроси, подливать ли в неё. |
| Серверной ветки нет | Уточни назначение, если тикет входит в объём. Создание ветки — отдельное решение. |

Запиши в карточке выбранные, пропущенные и спорные ветки с причинами. Для ограничения «только в текущую MOB» проверяй именно её. Спорное назначение остаётся на паузе до ответа пользователя.

## Подготовить отдельную копию

Используй выделенную папку портфеля в `~/working-copies/`. В уже существующей копии проверь origin, текущую ветку, индекс и незавершённые операции **до** переключения или вызова хелпера. `git hh-clone` для существующей папки может выполнить `pull`. Если копия занята другой работой, создай соседнюю для этой задачи. Основную рабочую копию обновляет пользователь.

Для новой копии подойдёт `git hh-clone <портфель>`. Когда веток несколько, можно сразу получить историю без ограничения глубины. В примере `mobs` — массив подтверждённых имён серверных веток:

```bash
git clone --filter=blob:none --no-tags --single-branch --branch "$portfolio" "$url" "$dir"
git -C "$dir" remote set-branches --add origin develop "${mobs[@]}"
git -C "$dir" fetch --no-tags origin
```

Перед каждым слиянием проверь `git merge-base` для обеих вершин. Если клон shallow и общей базы не видно, догрузи историю обеих веток. Запиши исходные SHA. Покажи dry-run по веткам: что во что вливается, какие сборки и публикации ожидаются. Для прогноза конфликтов используй `git merge-tree --write-tree`. Второй прогноз делай уже от проверенного коммита портфеля.

## Две фазы

1. **Develop → портфель.** Начни с серверной вершины портфеля. Влей выбранный SHA `origin/develop` через `git merge --no-ff --no-commit <SHA>`. Разбери конфликты по правилам ниже. Зафиксируй согласованный результат с учётом правил проекта, собери его и выполни разрешённый push. Сверь опубликованный SHA через `git ls-remote` и запиши его в карточку. Он служит источником для всех MOB.
2. **Портфель → активные MOB.** Для каждой выбранной MOB освежи её серверную вершину и проверь, что ветка и PR всё ещё активны. Влей в неё опубликованный SHA из первой фазы. Повтори ревью конфликтов, сборку и публикацию для этой MOB. Если целевая ветка уже содержит исходный SHA (`git merge-base --is-ancestor`), отметь «уже содержит» и переходи дальше. Это же правило действует при повторном запуске первой фазы.

### Ревью каждого конфликта

До коммита зафиксируй перечень конфликтных путей и собери для каждого решения основания: что делала общая база, зачем меняли поведение в обеих ветках, какой результат получит пользователь. Если требования несовместимы или выбор неясен, покажи варианты и задай конкретный вопрос.

Для каждого слияния с конфликтами отправь **guided review в Plannotator Inbox**. Вызови `get_guide_brief`, затем `submit_guide` с точным unified diff и пояснением каждого разрешённого фрагмента. В Git с `ort` изменения после автоматического слияния видны через `git diff AUTO_MERGE -- <конфликтные пути>`. Сверь покрытие с первоначальным списком, включая переименования, удаления и выбор одной стороны целиком. Если такой выбор не виден в diff, добавь сравнение с отличающейся стороной и объясни его. Укажи обе ветки, SHA и почему итог сохраняет требования каждой стороны либо какую уступку предстоит согласовать.

Сохрани ссылку или ID обсуждения в карточке. Дождись решения по этому слиянию. Вопрос из ревью требует ответа, а изменившийся после замечаний diff — обновлённого guided review. Если Inbox недоступен, спроси, где провести ревью. Учитывай разрешения на коммит и push, данные для текущего запуска.

### Сборка, публикация и завершение

На каждой изменённой ветке собери итог с помощью проектной процедуры сборки. Для приложений соискателя и работодателя минимум — `ApplicantHH` и `EmployerHH`. Сравни результат с прежней вершиной **целевой** ветки. Добавь затронутые расширения, тестовые или самостоятельные таргеты, если две основные схемы их не компилируют. Запиши SHA, схемы и результат. Совпадение без текстовых конфликтов тоже требует сборки.

При ошибке сохрани первую причину из лога и сверь код обоих родителей. Однозначную ошибку интеграции исправь и пересобери итоговый коммит. По спорному или постороннему исправлению спроси пользователя. Публикуй только проверенную вершину обычным push в явно указанную ветку. Если серверная вершина сдвинулась, обнови данные и повтори затронутые проверки перед публикацией.

В карточке сведи по каждой ветке исходный и опубликованный SHA, проверки и причину пропуска, если он согласован. При возобновлении сверь записи с сервером. Закрой карточку, когда Git подтверждает обе связи предков для всех включённых веток, а по каждому спорному назначению есть решение. При частичном успехе сохрани опубликованные результаты и оставь конкретный следующий шаг в той же карточке.
